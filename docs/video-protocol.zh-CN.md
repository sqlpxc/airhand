# 视频协商与接收端反馈

[开发](development.zh-CN.md) · [English](video-protocol.md)

本扩展在信令 v9、会话 v1 上通过 `features::session::VIDEO_MODEL`（bit 2）协商，不改变现有消息编号、ACK 语义或 24 字节媒体基础头。类型定义在 `crates/airhand-proto/src/video.rs`，会话状态在 `crates/airhand-link/src/video.rs`；Rust、TypeScript 和 Kotlin 使用共同的 JSON/媒体包样例。

本阶段实现了能力与偏好的分离、实际配置下发、帧与配置关联，以及约每 200 ms 一次的接收端反馈通路。反馈保存为可供策略读取的最新样本，2 秒没有更新就过期。现有 ABR 仍使用传输 ACK 和阻塞信息；根据解码反馈自动调整分辨率/帧率的策略需要另行实现和标定。可替换媒体流只预留身份模型与能力编号，当前仍使用固定视频流。

**四个模型的职责**

| 类型 | 发起方 | 含义 |
|---|---|---|
| `ReceiverCapabilities` | 控制端 | 解码器可接受的格式及已知硬限制 |
| `ViewRequest` | 控制端 | 用户/当前视图希望的输出，以及递增的 `requestId` |
| `VideoConfig` | 被控端 | 实际选定的编码格式、尺寸、帧率上限和目标码率，以及配置身份 |
| `VideoFeedback` | 控制端 | 某个配置下的接收、解码、提交显示进度与待处理状态 |

`ReceiverCapabilities.codecs` 是 1–16 个不重复的格式声明，每项包含 `codec`、可选的 `maxWidth`、`maxHeight`、`maxFps`。宽高为已知时至少 64，帧率为 1–120。`null`/缺字段表示没有这项信息，不能把它解释成“任何尺寸都能解”。最大宽、高、帧率分别描述必要限制，不承诺任意组合（例如最大宽 × 最大高 × 最大帧率）均能工作，也不代表实际吞吐。浏览器无法可靠查询硬限制，因此填 null；Android 使用所选解码器公布的范围，现有的尺寸组合检查继续保留。

`ViewRequest.preference` 复用 `QualitySettings` 表示期望值，不能用它扩大硬限制。初始请求编号是 0，后续设置命令在共享链路层转换成编号递增的 View。新端之间不把设置变化再当成能力变化。被控端先求可用编码格式交集，再将帧率、尺寸限制到接收端可接受范围；无交集是明确失败，不能擅自假设接收端会解 H.264。编码器实际输出也要再次检查（硬件回退可能改变格式）。第一版能力声明在会话期间固定；设备能力变化需要重新协商会话，普通画质调整不需要。

`VideoConfig.fps` 是选定帧率上限，`bitrateKbps` 是交给编码器的目标值，不是测得的瞬时输出帧率/码率。配置可能因为 ABR、编码器回退或共享编码而与请求不同。`requestId` 表示产生这份配置时使用的观看请求，不表示严格满足全部偏好；对同一请求可以报告多份实际配置。Android 将选择快照的版本传过 JNI 并随编码器输出返回，正在路上的旧编码器输出仍引用旧请求，不能把尚未应用的设置标到旧画面上。

**配置、流身份和包头**

`VideoContext` 包含非零 `configId` 和 `MediaInstance { streamId, generation }`。配置编号在会话中递增、不重用；实际参数/所采用的请求改变，或者同参数的编码器被重建时都分配新编号。帧序号继续在整个会话内递增，允许按原规则绕回，配置变化不重置 ACK 序号。

当前只接受 `(streamId=0, generation=0)`。`configId` 是配置身份，`generation` 是未来的传输实例身份，两者不能混用。重新编码或改变码率可以改变 configId，而无需重建网络流；将来替换传输实例需要递增 generation 并使用独立的密码学计数空间。

协商成功且握手带有有效 VideoOffer 时，视频包使用 36 字节头：

| 偏移 | 内容 |
|---:|---|
| 0–23 | 原媒体头；flags 的 bit 1 表示携带 VideoContext；header length 为 36 |
| 24 | `configId: u32 LE` |
| 28 | `streamId: u32 LE` |
| 32 | `generation: u32 LE` |
| 36 起 | 原视频负载，仍是 Annex-B / OBU |

旧的 key 标志仍为 bit 0。解码负载始终按包里的头长度定位。没有协商扩展时继续发 24 字节头，不产生新控制消息。

配置通知与视频走不同 QUIC 流，允许任一方先到。帧头携带的完整 context 用来关联运行反馈；不能因为配置通知尚未到达就错误地把视频归入上一配置。现阶段解码仍使用原媒体头及码流内的配置数据，不依赖跨通道的配置通知先到。界面只保存最新的配置通知，旧解码回调不能更新新 context 的反馈。

**反馈的精确定义**

反馈是累计快照，同一 context 下 sampleId 严格递增，适合“只保留最新值”的发送槽。配置变更后累计计数重新开始；session 失效后取消采样任务。界面收到第一帧带 context 的视频后开始采样，有变化或仍有待解码帧时最多每 200 ms 发一次。静止且已处理完的画面不会持续发送空反馈。

| 字段 | 语义 |
|---|---|
| `receivedSeq` | 最新收到的帧；不等同于已成功解码 |
| `decodedSeq` | 最新完成解码的帧；还没有时为 null |
| `presentedSeq` | 最新提交给 Canvas/Surface 显示的帧；还没有时为 null |
| `pendingFrames` | 等待解码完成的帧数，排除为了音画同步而刻意等待的帧 |
| `oldestPendingMs` | 最老待解码帧已经等待多久，包含解码器内部排队和处理 |
| `decodeTimeUs` | 从提交到解码输出的平滑耗时，包含解码器内部排队，不是纯 GPU 执行时间 |
| `droppedFrames` | 本 context 下接收端主动丢弃的累计帧数 |
| `decoderErrors` | 本 context 下观察到的解码器失败累计次数 |

`presentedSeq` 只说明已提交给渲染接口，不能声称是屏幕物理扫描输出时间。Surface 定时显示可以早于实际呈现时刻提交。反馈中的时长均由接收端本机单调时钟计算，不拿两台设备的绝对时钟相减。

被控端拒绝不同 context、重复/回退的 sampleId、回退的累计计数、超出该配置帧范围的进度和不合理的时长。接收反馈不释放任何视频发送窗口，原有 Ack 才负责流控。反馈迟到或缺失本身不导致会话断开。

对于未来的自适应策略，推荐分别处理网络拥塞和接收端处理能力：网络压力影响目标码率；持续的待解码数量/时长增长影响分辨率或帧率；主动音画同步等待不能当作拥塞。策略应有持续时间阈值、恢复迟滞和用户选择的上限，避免每个样本都重建编码器。

**协商与兼容规则**

| 注册项 | 编号 |
|---|---:|
| 会话能力 `VIDEO_MODEL` | bit 2 |
| `ControllerIntro.video: Option<VideoOffer>` | 字段 7 |
| `ControllerMsg::View` | 消息 9 |
| `ControllerMsg::VideoFeedback` | 消息 10 |
| `HostMsg::VideoConfig` | 消息 12 |
| 视频 context 标志 | 视频 flags bit 1 |

新的结构体使用带数字字段的 CBOR map，新增字段必须可选或有明确默认行为。控制端只有在前端提供有效接收能力时才在加密的 ControllerIntro 中声明 VIDEO_MODEL；被控端声明本机实现支持后，两边取交集。声称支持而缺少 offer、初始 requestId 非 0 或能力声明非法，都是握手错误。

旧端继续读取初始 `settings`，跳过新的可选 offer；新端收到旧端的能力位后回退到旧消息、旧包头、旧设置。`SessionInfo` 和旧的 `Encoder` 界面事件保持兼容，实际配置另用 `videoConfig` 事件。共享样例验证 Rust、TypeScript、Kotlin 的 JSON 形状，v9 golden tests 固定现有及新消息的编号和字节。

**可替换媒体流的预留范围**

信令能力 `MEDIA_INSTANCES` 预留 bit 0，会话能力同名项预留 bit 3；两者当前都不在 SUPPORTED 中。类型里预留 streamId/generation，接收路径主动拒绝非零实例。中转仍使用 AHS2，一条 lane 只配对一次。

以后实现替换时至少需要同时完成以下契约，才能宣告这两个能力：

1. 信令协商确认中转支持新的流头/路由身份，流配对键包含 `(sessionId, lane, streamId, generation)`；控制通道保持独立存活。
2. 端到端的可靠控制消息声明并确认切换目标；新视频从独立可解码点开始，明确何时放弃旧实例和过期帧。
3. 密钥派生绑定方向、逻辑流和 generation，或使用等效的全局唯一 nonce 设计；不能把同一把密钥的计数器重置为零。
4. 新流头的实例身份由端到端认证绑定，拒绝旧 generation 重放与跨实例搬运；每会话实例数和在途资源有界。
5. 增加替换中断、旧流迟到、跨流重排和旧中转回退测试。

当前实现不发送新流头、不重开视频 lane，也不承诺能够丢弃已进入可靠流的数据。预留使配置和反馈从一开始就能标识未来的实例，并避免把尚未实现的传输行为误报为已支持。
