# Security

## Relay server and control codes

- TLS 1.3 throughout (QUIC); the client verifies the server by **certificate fingerprint pinning**. Without a configured fingerprint the server's certificate is remembered on the first connection (trust on first use: `[server_trust]` in `config.toml`, Settings on Android, `server-trust.txt` for the web console), and a different certificate is refused afterwards
- Brute-force protection: at most 20 failed attempts per IP (IPv6 grouped by /64) per 10 minutes, and each failure adds a 400 ms delay
- When a code exists but its host isn't ready (still registering, or disconnecting), the answer is exactly the same as for a code that doesn't exist (counted as a failure, delayed the same way), so response timing doesn't reveal whether a code exists
- Requests with the right code are rate limited too. Every request takes one of the host's session slots, and a phone asks its user each time, so one IP (IPv6 grouped by /64) can start at most 6 connections per minute to the same host (`AIRHAND_CONNECTS_PER_MINUTE`; requests with a resume token count as well), and a phone keeps at most 2 requests waiting for your answer and turns further ones away. If someone who knows the code keeps pestering a host, **change its control code**
- Registering can't be used to probe codes: getting a code back requires a secret the server issued **for that code** (signed with the server's own key, which is kept in `airhand.db`, so it still works after a restart). Without one the host gets a fresh code whether or not the code it asked for is in use. Fresh codes are limited per network (30 per 10 minutes per IPv4 address / IPv6 /48, `AIRHAND_NEW_CODES_PER_IP`), so codes can't be hoarded
- Resume tokens: when a controller connects, the server gives it a token, and the controller presents it when reconnecting. The first half of the token is the server's signature (with its own key) over the control code, proving the holder connected to that code before; the second half is derived from the host's code and secret (it can't be computed or reversed without the secret). Requests with a token don't count as failures and aren't subject to the guessing limit, so however long a host stays offline, neither automatic reconnects nor opening an offline device from My devices use up the guessing allowance of the IP (or of a web console sharing one IP). A token that wasn't issued by the server for that code always gets the same answer, whether or not the code exists or is in use, so tokens can't be used to guess codes. A token stops working when the host changes its code, and when the user at the host **disconnects all controllers** (the server then gives the host a new secret, so a disconnected controller can't come straight back with its token; it would need the control code again). If the host gets disconnected while changing its secret and never receives the new one, it asks the server to change it when it registers next time (by then the server may have restarted and remember nothing), so the old secret can't become valid again and bring the old tokens back
- Getting a control code back after a reconnect requires a random secret, so nobody else can claim it
- Server resources: at most 128 simultaneous connections per IP (IPv6 /64, `AIRHAND_MAX_CONNS_PER_IP`), and the relay's QUIC flow-control windows are sized for forwarding (4 MiB per stream, 16 MiB per connection), so a peer that stops reading can only make the server buffer a few MiB for it
- Fixed control codes: the server only stores a hash of the host's secret (in `airhand.db`), so the database can't be used to claim codes. On Windows the host's secret is encrypted with DPAPI for the SYSTEM account, so a copied `config.toml` doesn't carry the code to another computer; on macOS / Linux `config.toml` is readable by your account only. **Change control code** releases the old code on the server
- My devices holds other computers' control codes: on Windows they're encrypted with your account (DPAPI), on macOS / Linux protected by the file permissions (600). Don't share `config.toml`
- The Windows host runs as SYSTEM so that it can operate UAC prompts and the sign-in screen: whoever can connect to it (knows the control code, and has paired or knows the pairing code) controls the computer with administrator rights. Give the codes only to people you trust; whoever sits at the computer sees who is connected and can disconnect them, change the control code / pairing code or quit Airhand
- The host's tray always shows who is controlling the computer; disconnect them or change the code with one click

## End-to-end encryption

TLS to the relay ends at the relay, so sessions get a second, end-to-end layer (protocol in `crates/airhand-proto/src/handshake.rs`):

- **Can't read, can't tamper**: at the start of every session the controller and the host run a Noise handshake on the control lane (X25519, ChaCha20-Poly1305, BLAKE2s). After that the picture, sound, keyboard and mouse input and the clipboard are encrypted end to end (AES-256-GCM), with one key per lane and direction, and every frame carries a counter (on the control and bulk lanes they must follow one another). The relay can't read them, and frames it changes, drops, replays or injects fail to decrypt, which ends the session. The session version and capability bits are negotiated inside the encrypted handshake, so the relay can't downgrade either side; there's no unencrypted session to fall back to
- **Knowing who's on the other end**: every device has a long-term key pair. The first time a controller connects to a computer it remembers that computer's public key (`host_key` in My devices, like SSH's known_hosts) and only accepts that key afterwards. If it differs, the controller says "the remote computer's identity changed", doesn't reconnect automatically, and can't simply be told to trust the new identity: that error arrives in the clear before the handshake completes, so the relay could forge it, and trusting a new identity without verification would let the relay get itself remembered as that computer. Once you've confirmed the computer really was reinstalled (it may also be someone impersonating it), enter its current pairing code from its tray to **pair again**: the pairing code authenticates the computer, and only a successful pairing records the new identity. For a phone (no pairing code), remove it from My devices and connect again. On the first connection both sides show the same 6-digit **safety code** (console: hover the control code in the toolbar; host: after the device in the tray's list of controllers; phone: in the connection request), so you can check that nobody is in between
- **Pairing code**: the relay assigns the control codes and uses them to find hosts, so **the relay knows every control code**; letting anyone in on the control code alone means trusting the relay (it could connect by itself). So desktop hosts ask for a **pairing code** by default: a controller that hasn't paired yet has to enter the 6-digit pairing code from the host's tray menu on its first connection. The pairing code never goes through the server; both sides turn it into a key with SPAKE2 (it's only a few digits: used directly as a key, a man in the middle could brute-force it offline from one recorded handshake; with SPAKE2 each attempt allows one guess). After 5 unsuccessful attempts (wrong codes, interrupted handshakes or timeouts), pairing is paused until the local user picks a new code. Each handshake reserves a local slot before starting: failures plus outstanding attempts cannot exceed 5. Changing the code or forgetting paired controllers prevents old handshakes from committing authorization. Once paired, the host remembers the controller (`[[paired]]` in `config.toml`), and the code isn't needed again
- **Replays**: a reconnect to a computer the controller already knows takes a single round trip (Noise IK), and the first message of that kind of handshake has no freshness: the relay could send a recorded one again. The host answers it, but only counts the controller as connected (shows it in the tray / the phone's list, starts capturing) after it decrypts the controller's first encrypted frame, which only the real controller can produce. So a replay can't make the host show a paired controller that isn't there, and reveals nothing
- The tray menu can **change the pairing code** and **forget paired controllers**; **Change control code** does both. `access = "open"` in `config.toml` turns pairing off: the control code alone is enough, which means trusting the relay
- Android hosts don't use a pairing code: by default they ask the person holding the phone (the request shows the safety code). A controller that was allowed reconnects without asking during the same sharing; it's recognized by its public key from the encrypted handshake, which the relay can't fake. Turning off "Ask before someone connects" means trusting the relay
- Where the keys live: the host's identity and pairing code in `[host]` in `config.toml` (encrypted with DPAPI for the SYSTEM account on Windows); the console's identity in `[controller]` (one per account on Windows, encrypted with that account's DPAPI); on Android in the app's private storage; for the web console in `controller-key.txt` (`AIRHAND_WEB_IDENTITY`)
- What the relay still knows: who connected to whom and when (control codes, IPs, the names and systems both sides report), and the size and timing of the traffic (typing rhythm may show in the timing)
- **Direct path** (see [How it works](architecture.md#direct-path)): the direct path carries the same end-to-end ciphertext, so it is exactly as secure as going through the relay. Who is on the other end is settled by mutual TLS: each end has a throwaway certificate whose fingerprint is exchanged over the encrypted, authenticated control lane, and TLS only accepts those two fingerprints, so a man in the middle can't impersonate either side. The control lane always has a complete copy on the relay, where the counters must still follow one another; frames dropped or delayed on the direct path change nothing. A direct path needs each end to know the other's IP address: the server only tells each end its own public address, and the candidates (including LAN addresses) are exchanged over the encrypted control lane, the host sending its own only after the session has started (after the local user allowed it). So someone who only knows the control code and hasn't been let in can't learn the host's address, and the relay never sees LAN addresses. The host only accepts direct handshakes while one of its sessions is offering candidates
- Web console: end-to-end encryption ends at the web console service (it is the controller); the browser talks to it over HTTPS / WSS. So the machine running the web console can see the picture; if it's the same machine as the relay, web console users effectively have no end-to-end encryption

## Web console

- The WebSocket only accepts pages from the same site (so other websites can't connect through your browser); an access password can be set (HTTP Basic login, then an HttpOnly, SameSite=Strict cookie; wrong passwords are answered with a delay); use HTTPS from other computers. The web console sees the picture too, so run it on a machine you trust. Everyone using it reaches the relay from that machine's IP, so they share the brute-force allowance
